## Q-1【障害・最重要】ENA_DYNISR はレベル1 限定か → **否。制約は「レベル」ではなく intpri**

**「レベル」という概念は ENA_DYNISR の検査連鎖のどこにも存在しない。**
本質的制約はただ1つ:

> **対応する `CFG_INT(intno)` の intpri がカーネル管理範囲内であること**
> （判定式は `intpri < TMIN_INTPRI` なら `E_OBJ`。`kernel/interrupt.py:411-416` /
> `kernel/interrupt.trb` に同一実装。エラー文言
> "interrupt service routine cannot handle non-kernel interrupt"）

貴ポートは `TMIN_INTPRI = -3` とのことなので、**CFG_INT で intpri を -3〜-1 に
設定できる intno なら ENA_DYNISR に使える**。標準的な Xtensa ポートの
intlevel↔intpri 対応（level N ↔ intpri -N）が貴側でも成り立つなら、
**レベル2・レベル3（= XCHAL_EXCM_LEVEL）まで成立し、レベル1 の枯渇は障害にならない**
——ただしこの対応関係は貴側 arch の実装事項なので貴側で確認されたい（ここだけ推測）。
レベル4 以上（intpri < -3）はカーネル管理外なので cfg 時点で E_OBJ になる。
まさにこの経路の回帰 cfg を本日追加した
（`tools/cfg_error_tests/dcre_dynisr_unmanaged_intpri.cfg` — CFG_INT としては合法だが
管理外の intpri に ENA_DYNISR して E_OBJ×2 を確認）。

**ENA_DYNISR の検査の全リスト**（両エンジン同一。`kernel/interrupt.py:386-451`）:

1. CLASS の囲みの中に書くこと（E_RSATR）
2. intno が `INTNO_CREISR_VALID` の範囲内（E_PAR）— この範囲は貴側 arch が定義する
3. 同一 intno の `CFG_INT` が存在（E_OBJ）
4. その CFG_INT と**同一クラス**であること（E_RSATR）— 実行コアはこれで決まる
5. **CFG_INT の intpri ≥ TMIN_INTPRI**（E_OBJ）← 本質的制約
6. 同一 intno に `DEF_INH` が無いこと（E_OBJ）— 貴側の DEF_INH 9本はここに掛かる
7. ENA_DYNISR が1個でもあるなら**システム全体で** `CRE_ISR` が1個以上（E_OBJ）
8. `AID_ISR(n)` n>0 なら**システム全体で** ENA_DYNISR が1個以上（E_OBJ）

**runtime 側の補足**: `acre_isr` に intpri/レベルの追加検査は無い。intno は
cfg が生成した opt-in 済みテーブル（`isr_queue_list`）の二分探索で解決され、
「不正 intno／CFG_INT 無し／未 opt-in／DEF_INH 競合」は**すべて runtime では
E_OBJ に合流する**（dcre 原典が一部 E_PAR とする点からの意図的乖離・文書化済み）。
貴側の `attachInterrupt` シムがエラーを弁別するなら、この点に注意。

## Q-2 静的 CRE_ISR と ENA_DYNISR の併存 → **できる。設計どおり**

貴側の理解は正確。詳細:

- ENA_DYNISR された intno の inthdr は、静的 CRE_ISR の有無にかかわらず
  **無条件にキュー走査（`_kernel_call_isr(...)` 1行）へ切り替わる**
  （`kernel/interrupt.py:482-523` の生成ロジック）。
- その intno 上の**静的 ISR は起動時に同じランタイムキューへ登録される**
  （`initialize_isr`、`kernel/interrupt.c:311-320`。isrid 昇順に enqueue され
  isrseq 0,1,2… を得る）。以後は動的 ISR と同じ **(isrpri, isrseq) 辞書式順**で
  呼ばれる。静的 ISR どうしの相対順序はインラインチェーン方式と一致するよう
  生成順を揃えてある。
- **`del_isr` は静的 ISR を拒否する**（`isrid <= tmax_sisrid` → E_OBJ、
  `kernel/interrupt.c:637-639`）。「既存の CRE_ISR を持つ intno を ENA_DYNISR に
  回す」使い方は、静的分が消せないだけで完全に成立する。

## Q-3 test_dcre5 の ISR_SIO 依存 → **意図的（アサーション2箇所で実使用）。ただしこちらで自立化する**

まず事実関係。ISR_SIO は「静的 CRE_ISR ≥1」ガードのためでは**ない**
（test_dcre5.cfg は自前の静的 `ISR_S2`/`ISR_S4` を INTNO1 に持つ。
`test/test_dcre5.cfg:29-31`）。依存は**テストロジック本体の2箇所**:

- `test/test_dcre5.c:424` `check_assert(erid > ISR_SIO)` —
  **別 cfg ファイル（syssvc 系）由来の静的 ID に対しても** 2レンジ ID 分割が
  成り立つことの検証（クロスファイル性が狙い）
- `test/test_dcre5.c:578` `check_ercd(del_isr(ISR_SIO), E_OBJ)` —
  自分が作っていない静的 ISR にも del_isr 拒否が効くことの検証

つまり「意図的だが代替可能」。**方針: こちらでテスト側を自立化する。**
具体的には test_dcre5.cfg 自身に独立な `CFG_INT`+`CRE_ISR`（新 INTNO、ENA_DYNISR
しない）を1本足し、上記2箇所の参照をそれへ差し替える。INTNO2 は
ドレインシナリオ（手順9）のため**動的専用を維持する必要があり**、そこには足さない。
クロスファイル検証の性格は少し弱まるが（同一ファイル内の静的 ISR になる）、
検証内容自体（2レンジ分割・静的 del 拒否）は保たれる。

**時期**: 現在走っている hardening pass のタスク完了後、最終回帰（全テスト・
全プリセット）に含めて検証してからコミットする。**完了したらコミットハッシュを
本文書末尾に追記する**ので、貴側は次回 pin 更新で拾えるはず。
（それまでは test_dcre5 を対象外にしておくのが安全。）

参考: test_dcre1〜4 は ISR/CFG_INT を一切参照しない（grep 確認済み）。

## Q-4 AID_*(n) の実用上の上限 → **cfg 側の上限検査は無い。効くのは RAM の線形増だけ**

1. **ID 空間**: cfg 側に `n` の大きさの検査は**存在しない**（`kernel/kernel.py` の
   `KernelObject.generate()` は合計するだけ）。ID は `signed int`。数十〜数百の
   予約で ID 空間が問題になることはない。
2. **テーブルサイズ**: 貴側の理解どおり **`.bss` が n に線形**。予約スロット1個あたり
   CB＋RAM 側 inib＋p_*cb 表(4B)＋order 表(4B) が増える。32bit での概算
   （構造体フィールド数からの算出。パディング未実測なので目安）:

   | オブジェクト | CB | inib(RAM) | 1スロット概算 |
   |---|---|---|---|
   | sem | 16B | 12B | 〜36B |
   | flg | 16B | 8B | 〜32B |
   | mtx | 20B | 8B | 〜36B |
   | dtq | 32B | 12B | 〜52B（+バッファは供給次第） |
   | pdq | 36B | 16B | 〜60B（同上） |
   | mpf | 24B | 20B | 〜52B（同上） |
   | isr | 20B | 20B | 〜48B |
   | cyc/alm | 24B前後 | 20-28B | 〜56B |
   | tsk | 50-70B+ | 35-50B+（TSKCTXB/TSKINICTXB は arch 依存） | 〜100-130B+（+スタック） |

   貴側実測の「`AID_MTX(16)` で .bss +480B（=30B/スロット）」は
   この概算（mtx 〜36B/スロット、順序表の有無等で前後）と整合する。
   **DRAM 13.6KB の制約下では、この表で予算を引くのが正攻法**
   （例: AID_SEM(64) ≈ 2.3KB — たぶん過大。実需要+α に絞るのを推奨）。
3. **探索コスト**: **O(n) ではなく O(1)**。空きスロットは FIFO free-list
   （双方向キュー）で、`acre_*` は `queue_delete_next` の定数時間 pop
   （空なら E_NOID）。O(n) ループは起動時の `initialize_*` だけで、
   acre/del のホットパスには無い。`setup()` で数十回呼んでも問題ない。
4. **落とし穴（想定内の注意のみ）**: (a) tsk/dtq/pdq/mpf で NULL 供給すると
   カーネルメモリプール（bump アロケータ・前回 R-2 参照）を使う。貴側の
   「tsk/dtq はユーザ供給（案B）、sem/mtx/flg はプール不使用（案A）」の切り分けは
   コードと完全に整合（sem/flg/mtx/cyc/alm/isr は TA_MEMALLOC/TA_MBALLOC に
   一切触れない — grep 0件）。(b) 予約数とは別に、`acre_tsk` 等の**新 E_PAR
   ガード**（サイズ乗算オーバーフロー検査）が hardening で入った — 極端な引数で
   E_NOMEM だったものが E_PAR になるケースがある。確定内容は前回文書の予告どおり
   `docs/qa-esp32s3-20260804.md` 末尾に追記する。

## 補足: 貴側の L1 枯渇問題への含意

Q-1 の結論により、**DEF_INH 9本を減らす工事は（ENA_DYNISR のためには）不要**の
見込み。レベル2/3 の空き intno に CFG_INT(intpri ∈ -3..-1相当)+ENA_DYNISR で足りる。
なお DEF_INH がある intno は検査6で拒否されるので、仮に L1 に空きを作っても
DEF_INH と同居はできない（分離が必要）点は変わらない。

## 追記（2026-08-04・メモリプール freelist 化）Q-4 補足の変更確定

Q-4 の 4.(a) で「tsk/dtq/pdq/mpf で NULL 供給するとカーネルメモリプール
（bump アロケータ・前回 R-2 参照）を使う」と述べた **bump アロケータの部分が
commit `a32afa1` で「バンプ＋完全一致サイズ再利用」へ変わった**
（詳細・実測 ROM 増分は `docs/qa-esp32s3-20260804.md` 末尾の追記を参照）。

- Q-4 の本旨（AID_*(n) の上限は RAM の線形増だけ・スロット表の概算）は
  **不変**（AID_* のスロット表はプールと無関係の静的確保）。
- 変わるのは NULL 供給時のプール劣化特性のみ：同一サイズの create/delete
  反復ではアリーナが痩せなくなった。貴側の「tsk/dtq はユーザ供給（案B）」の
  判断は引き続き成立するが，その根拠のうち「プールは単調に痩せる」は
  過去形になった点だけ訂正する。
- 割付1件あたり +4B/+8B のヘッダが付くため，NULL 供給を使う場合の `mpksz`
  見積りには割付件数×ヘッダ分を積み増すこと。
