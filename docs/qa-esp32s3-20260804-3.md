## 2番【質問】`_kernel_mpksz = 0` の構成でコードサイズが増えるか → **貴側の理解は正しい。実測値も出た**

### (a) 「呼ばない関数も .text に乗る」は正しい（3点の事実で確認）

1. fmp3_core の CMake は上流 `sample/Makefile:302` に忠実に `ALLFUNC` を定義しており
   （`CMakeLists.txt:560-562`）、`kernel/allfunc.h:54` が `TOPPERS_kermem` を定義する。
   したがって既定メモリプール実装（`kernel/startup.c` の `#ifdef TOPPERS_kermem` 節）は
   **無条件にカーネル単一 .o に入る**。
2. `_kernel_mpksz = 0` の構成では実行時に `mpk_valid = false`（`startup.c` の
   `mpksz > 0 && mpk != NULL` ゲート）となり全経路が死ぬが、**flash 上のコードは残る**。
3. 翻訳単位粒度の `--gc-sections` では落ちない——`startup.c` には `sta_ker` が居るため
   TU 全体が必ずリンクされる。

### (b) 再利用拡張の実装量 → **実測 text +244B**（見積り +100〜250B の範囲内）

拡張は**実装済み**（commit `a32afa1`、現在タスクレビュー中）。同一ビルドパス A/B
（musca_b1-2core、Cortex-M33 Thumb2、直前コミット caa1097 との比較）で

> **text +244B / data +0 / bss +0**

RAM 側の増分は「プールを使う場合のみ」発生する（生存割付あたり +sizeof(size_t)、
プール制御ブロック +sizeof(void*)）ため、**プール不使用の貴構成では RAM 増ゼロ・
flash +244B 前後**が予想値になる（貴側の Xtensa では命令セットが違うので絶対値は
前後する。貴側の段0 同様の測定で確認されたい）。

### (c) flash が問題になった場合の既存の逃げ道（参考・依頼ではない）

`OMIT_MEMPOOL_DEFAULT`（`startup.c` の `#ifndef` ガード、dcre 由来・今回の拡張でも
不変）を定義して4関数（initialize/malloc/aligned_alloc/free_mempool）をスタブ
（false/NULL 返却）で供給すれば、既定実装は丸ごと消せる。貴側ビルドで
`-ffunction-sections` を足す手もあるが、それは貴側の判断事項。

## 1番【訂正の受領】動機帰属は spec から削除済み

設計 spec（`docs/superpowers/specs/2026-08-04-fmp3-mempool-freelist-design.md` §1.2、
commit `a5818cb`）に「esp32_s3 は受益者ではない（プール不使用・案B へ回帰しない）」を
貴側 REPLY3 への参照つきで明記した。貴側の実測は「同一サイズの create/delete
サイクルが実在することの証拠」としてのみ引用している。

---

## 3番への補足（先回り回答）: acre_tsk の丸めあふれ検査（H-4）は案B でも対象

確認中とのことだった件——**対象になる**。`kernel/task_manage.c:184` の
`CHECK_PAR(stksz <= SIZE_MAX - (sizeof(STK_T) - 1))` は `stk` の NULL 判定より
**前**にある無条件検査（hardening 最終レビューで独立確認済み）。ユーザ供給
スタック（`stk != NULL`）でも極端な `stksz` は E_PAR で拒否される。

## 5番【予告の受領】INTNO3

S3/LX6 で共通番号が取れなかった場合の相談はいつでも受ける。こちら側の選択肢
（テスト cfg 側での対処等）も併せて検討可能。

## 追記（2026-08-04・クローズアウト）メモリプール freelist 化 完了

実装（`a32afa1`）・テスト（`b63c7c1`、test_dcre6 新設・変異control実測）・
文書更新（`docs/dynamic-creation.md` §6/§7.1/§7.5、本シリーズ qa 3文書への
変更確定追記）がすべて完了した。ROM/RAM 実測値は本文書冒頭（2番の回答）の
とおりで変更なし（text +244B / data 0 / bss 0、`_kernel_mpksz = 0` の貴側構成は
挙動・コードサイズとも無関係）。

**最終コミット範囲**: `a32afa1`（実装）〜本追記を含む文書更新コミット
（`docs(dcre): メモリプール freelist 化の文書更新と最終回帰`、`git log --oneline`
で件名検索のこと。ハッシュの自己参照を避けるため本文には埋め込まない）。

**pin 推奨の更新**: 全体クローズにともない，推奨 pin を本コミット（このタスクの
コミット）以降へ更新する。貴側構成（`_kernel_mpksz = 0`）への影響は今回も無いため
急ぐ理由はないが，次回 pin 更新時に本変更一式が入る。

**追記（最終レビュー後の確定）**: 全体最終レビューの指摘により
`7a8d7e4`（fix(kernel): mempool freelist のプール終端はみ出し穴を閉じる）を
追加した——64bit＋**ユーザ供給 mpk** で `mpksz` が `sizeof(size_t)` の倍数で
ない場合にプール末尾の解放が領域外へ 4B 書き込みうる潜在穴を、
`initialize_mempool` の limit 切り下げ（+8B text）で構造的に閉じたもの。
貴側構成（プール不使用）には引き続き無関係。**確定した推奨 pin は
`7a8d7e4` 以降**。ROM 増分の最終値は freelist 化一式で text +252B
（+244B 実装 +8B 終端修正）/ data 0 / bss 0。
